01 · Introduction

Welcome to Woody

Woody is the group's dedicated Linux workstation for computational chemistry: protein-ligand docking, co-folding, and virtual screening at real scale. This guide gets you from "I've never used a terminal" to "I can run my own workflows responsibly."

What Woody is

  • A shared, purpose-built Linux machine (Rocky Linux) with serious CPU, RAM, and GPU resources for cheminformatics work.
  • A tool the whole group depends on — your session shares the same 64 threads, 503 GiB of RAM, and 4 GPUs as everyone else's.
  • Accessed exclusively over SSH. There is no monitor, mouse, or desktop attached to it — everything happens through your terminal.

What Woody is not

  • Not your laptop. Files, environments, and running programs live on Woody, not on the machine in front of you.
  • Not a scheduled HPC cluster. There is currently no job scheduler (no SLURM, no PBS). Resources are shared informally — see Section 09.
  • Not unlimited or automatically backed up. Treat /scratch as working space, not an archive.
  • Not a sandbox for irreversible experiments. There's no undo for a misplaced rm -rf, and the system Python is shared infrastructure other people's software depends on.
🟢 QUICK SUMMARY Woody is a shared scientific instrument, not a personal computer. Everything you do — the space you use, the jobs you run, the mess you leave — affects the next person who logs in. This guide is about using it well.

The philosophy of using a shared scientific workstation

Four habits will make you a good citizen of Woody, and they're the thread running through every section below:

  1. Use resources responsibly. Check what's free before you claim it — especially GPUs.
  2. Keep things organised. A predictable project layout means you (and your successors) can find things in six months.
  3. Make workflows reproducible. An environment and a README beat a folder of scripts only you understand.
  4. Leave it in a good state. Clean up scratch space, don't touch other people's files, and don't hold four GPUs hostage overnight for a job that needed one.

03 · Connecting to Woody

Connecting to Woody

Your laptop is just a window onto Woody. Nothing you run through this connection uses your laptop's CPU, RAM, or GPU — it all happens on the remote machine. The connection is:

ssh -X -Y username@woody.chem.gla.ac.uk

-X and -Y enable X11 forwarding, which lets graphical chemistry applications (e.g. molecular viewers) running on Woody display their windows on your screen. Without them, GUI tools will fail to open.

Setting up the woody shortcut

Typing the full command every time gets old fast. Set up a shortcut once and just type woody from then on.

🔵 HOW TO — Option A: SSH config (recommended)

Create or edit ~/.ssh/config on your laptop and add:

Host woody
    HostName woody.chem.gla.ac.uk
    User your_username
    ForwardX11 yes
    ForwardX11Trusted yes

Now ssh woody works from Git Bash, WSL, or any terminal that reads this file.

🔵 HOW TO — Option B: Bash alias

Add this line to ~/.bashrc (or ~/.bash_profile):

alias woody="ssh -X -Y your_username@woody.chem.gla.ac.uk"

Then run source ~/.bashrc once, or just open a new terminal window.

Which terminal to use

OptionNotes
Git BashWorks out of the box on Windows. Simplest option for most students.
Windows TerminalGood if you're already running PowerShell/Command Prompt profiles; SSH works the same way.
Ubuntu (WSL)Optional, but useful if you want a full local Linux environment to test scripts before running them on Woody.

The first time you connect, you'll see a prompt about the host's authenticity (a fingerprint). This is normal — type yes to continue. You should only see it once per machine.

🔴 COMMON MISTAKES
  • Forgetting -X -Y, then wondering why a graphical viewer won't open.
  • Retyping the full SSH command every session instead of setting up the shortcut once.
  • Assuming files you see on Woody are also on your laptop (they're not — see Section 05).

Paths, permissions, and getting unstuck

Absolute paths start from the root, e.g. /data/ligand_libraries/set3. Relative paths start from where you are, e.g. ../results/run1. When in doubt, use pwd to check where "here" actually is.

Permissions: ls -l shows something like -rwxr-xr-x — read/write/execute for owner, group, and everyone else. You'll rarely need to change permissions, except making your own script runnable with chmod +x script.sh.

History: press ↑ to recall previous commands, type history to see a list, or press Ctrl+R to search your history interactively.

Getting help: man command opens the manual page; most commands also accept --help for a quick summary.

🔴 COMMON MISTAKES
  • rm -rf deletes permanently — no confirmation, no undo. Double-check your path before pressing Enter.
  • Wildcards are powerful and dangerous: rm * in the wrong directory deletes everything in it.
  • Linux is case-sensitive: Results/ and results/ are different folders.
05 · Files & Storage

Files & Storage

Your laptop and Woody are two separate computers. Files don't move between them automatically — you have to transfer them deliberately, and you have to choose the right storage location once they're there.

/home 632 GB · personal

Your scripts, environments, and small personal files. Think of it as your desk, not your warehouse.

/scratch 3.7 TB · working space

Active calculations, docking runs, and temporary output. Working space, not a permanent archive — clean up when a run is done.

/data 73 TB · shared

Large shared datasets: ligand libraries, reference structures, results worth keeping long-term.

⚗ CHEMISTRY NOTE A single virtual screen against a library of tens of thousands of compounds can generate far more temporary output (poses, logs, intermediate files) than /home is built to hold. That's exactly why /scratch exists — and why the source ligand libraries themselves belong in /data, not copied into your home directory.

Moving files between your laptop and Woody

Use scp for individual files:

# Upload a file from your laptop to Woody
scp local_file.pdb username@woody:/home/username/project/

# Download a file from Woody to your laptop
scp username@woody:/scratch/username/results/output.csv .

For whole folders or large datasets, rsync is more robust — it can resume interrupted transfers and only copies what's changed:

rsync -avz local_folder/ username@woody:/data/username/project/
🟡 GOOD PRACTICE
  • Small scripts and environments → /home. Active runs → /scratch. Shared/large data → /data.
  • Never let /scratch hold the only copy of a result you care about — move anything worth keeping to /data or off the machine entirely.
  • Use rsync instead of repeated scp calls when moving large or growing folders.
06 · Project Organisation

Project Organisation

A consistent folder layout means you — and whoever inherits your project — can understand it in five minutes rather than an afternoon.

project/ ├── README.md ← what this project is, and how to reproduce it ├── input/ ← starting structures, ligand lists ├── scripts/ ← your code ├── environments/ ← conda/venv definitions (see Section 07) ├── docking_runs/ ← raw run output (usually in /scratch) ├── results/ ← processed, kept output └── analysis/ ← notebooks, figures, summaries

Your README.md doesn't need to be long. It should answer: what is this project, when did you start it, what environment does it need, and how would someone reproduce your last result?

🟡 GOOD PRACTICE
  • Use descriptive, underscore-separated names: 2026-07_kinase_screen, not test2.
  • Keep raw run output in /scratch, and copy only what you've verified matters into results/ in /data.
🔴 COMMON MISTAKES Folders named final_v2_REAL_final, and one-off scripts nobody documented — including you, in three months.
07 · Software & Environments

Software & Environments

Woody's system software is shared infrastructure. Isolating your own tools protects both your work and everyone else's.

🔴 DO NOT MODIFY SYSTEM PYTHON Woody's system Python is version 3.6.8, and existing software (including cryo-related tools) depends on it exactly as it is. Never sudo pip install anything, and never install packages globally.

Use isolated environments instead

Conda or Mamba environments give you your own private, disposable Python setup per project — install whatever you need without touching the system, and without breaking anyone else's work.

This guide covers the concept only; a full walkthrough of installing and configuring scientific software (OpenEye, RDKit, and friends) is coming in Volume 2.

Modules (Lmod)

Woody also has Lmod for a small number of shared libraries:

module avail        # list what's available
module load mpi/openmpi-x86_64
module list         # see what you currently have loaded

Currently available: mpi/openmpi-x86_64 and pmi/pmix-x86_64. Modules are a secondary tool here — your own conda/mamba environments will do most of the work.

🔴 COMMON MISTAKES
  • Global pip install outside of an environment.
  • Any use of sudo with pip or conda — you shouldn't need it, and if you think you do, ask first.
08 · Software

Software

Guides for specific scientific software installed on Woody. More tools get their own subsection here over time.

AlphaFold3

🟢 QUICK SUMMARY AlphaFold3 predicts the 3D structure of a protein — or of a protein bound to a peptide, macrocycle, or small molecule. It doesn't dock the way AutoDock/Glide does (scoring poses against a fixed receptor); it co-folds the whole complex from scratch in one pass, giving back one predicted structure with a confidence score, no pose list to browse.

Installed and verified working. Weights and the ~630GB genetic database set are shared on /data — nothing to download per person, you just need to be in the docker group.

🔵 HOW TO — fold a single protein

1. Get a sequence (UniProt, or wherever your target comes from). 2. Save an input JSON in ~/af3/input/:

{
  "name": "my_protein",
  "sequences": [{ "protein": { "id": "A", "sequence": "YOUR_SEQUENCE_HERE" } }],
  "modelSeeds": [1],
  "dialect": "alphafold3",
  "version": 4
}

3. Run it:

docker run -it \
    --volume $HOME/af3/input:/root/af_input \
    --volume $HOME/af3/output:/root/af_output \
    --volume /data/20260825_AndrewR_af3/models:/root/models \
    --volume /data/20260825_AndrewR_af3/databases:/root/public_databases \
    --gpus all \
    alphafold3 \
    python run_alphafold.py \
    --json_path=/root/af_input/my_protein.json \
    --model_dir=/root/models \
    --output_dir=/root/af_output

Two stages run back to back: a CPU-only genetic-search stage (slow — minutes) then GPU inference (fast — usually under a minute). Results land in ~/af3/output/<name>/<name>_model.cif.

🟢 REAL RESULT — FFA4 monomer (297 aa) ranking_score 0.91 · ptm 0.88 · iptm null (single chain — expected, not an error) — data pipeline 441s, inference 53s on one A5500. ptm/iptm above 0.8 is confident; below 0.6, treat the prediction with real skepticism.

Docking: protein-protein and protein-peptide/ligand complexes

Add a second entity to sequences and AlphaFold3 predicts the joint complex directly — no separate docking step.

🟣 CHEMISTRY NOTE — macrocycles & peptidomimetics AlphaFold3's protein entity only understands standard linear natural-amino-acid chains — no head-to-tail cyclization, disulfide staples, D-amino acids, or N-methylation. For a macrocyclic peptide or peptidomimetic, represent it as a ligand entity via its SMILES string instead (from ChemDraw, RDKit, PepWiz, or hand-drawn) — SMILES ring notation encodes the macrocycle directly. This is exactly what a DeepMind AlphaFold3 maintainer recommends for this case (GitHub issue #242): "specify the whole peptide plus covalently bound ligand as SMILES string, treating short peptide as a small molecule."
🟢 REAL RESULT — FFA4 + TUG-891 (native agonist, experimental EC50 ~0.2–0.4 µM) iptm 0.94 · ranking_score 0.95 · no clashes — a strong, well-calibrated result on a molecule with known real affinity. Good benchmark for judging your own macrocycle/peptidomimetic runs against.
🟡 GOOD PRACTICE — shared GPUs Woody has 4 GPUs, shared. Check nvidia-smi first, then pin your run to a free one instead of grabbing all of them: --gpus device=2 (zero-indexed).
🔴 COMMON MISTAKES
  • Out-of-memory during inference — our 24GB cards are below AlphaFold3's officially verified 80GB tier. Add XLA_PYTHON_CLIENT_PREALLOCATE=false, TF_FORCE_UNIFIED_MEMORY=true, XLA_CLIENT_MEM_FRACTION=3.2 as -e flags to enable memory spillover to system RAM.
  • SMILES strings containing \ need it doubled to \\ in JSON, or the file won't parse.
  • A run seeming "stuck" with no GPU activity is normal — the CPU genetic-search stage can take 10+ minutes before inference even starts.

Full parameter reference, glossary, and more worked examples (protein-protein, other ligand types): the AlphaFold3 how-to guide, kept as a plain file on Woody at ~/af3/HOWTO.html (styled) / ~/af3/HOWTO.md (markdown source) — open directly, no separate publishing step.

09 · Monitoring Resources

Monitoring Resources

With four GPUs and 64 threads shared across the group, checking what's free before you start is basic courtesy — and it saves you from launching a job into resources that are already spoken for.

CommandShows you
nvidia-smiGPU utilisation and memory usage, per card.
topLive CPU and memory usage by process. Press q to exit.
htopA friendlier version of top, if installed.
free -hTotal, used, and free RAM, in human-readable units.
df -hDisk space free on each mounted volume (/home, /scratch, /data).
du -sh folderTotal size of a specific folder — useful for finding what's eating space.
🟡 GOOD PRACTICE Run nvidia-smi and free -h before launching anything large. If all four GPUs already show near-full memory, your job will either fail or slow everyone down — check first, or ask in the group chat.
10 · Running Long Computational Workflows

Running Long Workflows

Woody currently has no job scheduler — no SLURM, no PBS, no automatic queue. That gives you flexibility, but also means nothing protects your job automatically, and nothing stops you from accidentally taking resources someone else needed.

The practical consequence: if your SSH connection drops or you close your terminal, any job running in that session dies with it — unless you've protected it.

Preparation
→

Keeping a job alive: tmux

🔵 HOW TO — run something long in tmux 
tmux new -s gpu2_screen_batch3     # start a named session
# ...run your job here...
# detach without stopping it: Ctrl+b, then d

tmux ls                            # list running sessions
tmux attach -t gpu2_screen_batch3  # reattach later, from anywhere

Your job keeps running after you detach — even after you close your laptop — because it belongs to the tmux session on Woody, not to your terminal connection.

screen works similarly and is a fine alternative if that's what you already know. For quick one-off jobs, nohup command & will also survive a disconnect, sending output to a file called nohup.out.

🟡 GOOD PRACTICE
  • Name your tmux sessions descriptively (tmux new -s kinase_dock_gpu1), not tmux new -s test.
  • With no scheduler enforcing fairness, a quick message to labmates about which GPU(s) you're using goes a long way.
