Computation

Using Woody

● Draft v1.0 Updated 2026-08-27
QUICK SUMMARY
Woody is the group's dedicated Linux workstation for computational chemistry: protein-ligand docking, co-folding, and virtual screening at real scale. This chapter gets you from "I've never used a terminal" to "I can run my own workflows responsibly." Woody is a shared scientific instrument, not a personal computer — everything you do affects the next person who logs in.

What Woody is

  • A shared, purpose-built Linux machine (Rocky Linux) with serious CPU, RAM, and GPU resources for cheminformatics work — Threadripper PRO 5975WX (32c/64t), 503 GiB RAM, 4× RTX A5500 (24GB VRAM each), 632GB /home, 3.7TB /scratch, 73TB /data.
  • A tool the whole group depends on — your session shares the same 64 threads, 503 GiB of RAM, and 4 GPUs as everyone else's.
  • Accessed exclusively over SSH. There is no monitor, mouse, or desktop attached to it — everything happens through your terminal.

What Woody is not: not your laptop (files/environments/programs live on Woody, not the machine in front of you); not a scheduled HPC cluster (no SLURM/PBS — resources are shared informally, see Monitoring below); not unlimited or automatically backed up (treat /scratch as working space, not an archive); not a sandbox for irreversible experiments (no undo for a misplaced rm -rf, and the system Python is shared infrastructure).

Four habits run through every section below: use resources responsibly (check what's free before you claim it, especially GPUs); keep things organised (a predictable project layout means you and your successors can find things in six months); make workflows reproducible (an environment and a README beat a folder of scripts only you understand); leave it in a good state (clean up scratch space, don't touch other people's files, don't hold four GPUs hostage overnight for a job that needed one).

First 10 minutes

If you only read one part before your first login, make it this one. Open a terminal (see Connecting below) and work through these eight commands.

woody                        # connect to Woody
pwd                          # where am I?
ls                           # what's here?
nvidia-smi                   # are the GPUs free?
df -h                        # how full is storage?
mkdir my_first_project       # make a folder that's yours
cd my_first_project          # step into it
pwd                          # confirm you're in the right place
QUICK SUMMARY
Connect, look around, check what's free, make a folder. That's it — everything else in this chapter is detail on top of these eight lines.

Connecting to Woody

Your laptop is just a window onto Woody. Nothing you run through this connection uses your laptop's CPU, RAM, or GPU — it all happens on the remote machine.

ssh -X -Y username@woody.chem.gla.ac.uk

-X and -Y enable X11 forwarding, which lets graphical chemistry applications (e.g. molecular viewers) running on Woody display their windows on your screen. Without them, GUI tools will fail to open.

Setting up the woody shortcut

HOW TO — Option A: SSH config (recommended)

Create or edit ~/.ssh/config on your laptop and add:

Host woody
    HostName woody.chem.gla.ac.uk
    User your_username
    ForwardX11 yes
    ForwardX11Trusted yes

Now ssh woody works from Git Bash, WSL, or any terminal that reads this file.

HOW TO — Option B: Bash alias

Add this line to ~/.bashrc (or ~/.bash_profile):

alias woody="ssh -X -Y your_username@woody.chem.gla.ac.uk"

Then run source ~/.bashrc once, or just open a new terminal window.

Which terminal to use

OptionNotes
Git BashWorks out of the box on Windows. Simplest option for most students.
Windows TerminalGood if you're already running PowerShell/Command Prompt profiles; SSH works the same way.
Ubuntu (WSL)Optional, but useful if you want a full local Linux environment to test scripts before running them on Woody.

The first time you connect, you'll see a prompt about the host's authenticity (a fingerprint). This is normal — type yes to continue. You should only see it once per machine.

COMMON MISTAKES
  • Forgetting -X -Y, then wondering why a graphical viewer won't open.
  • Retyping the full SSH command every session instead of setting up the shortcut once.
  • Assuming files you see on Woody are also on your laptop (they're not — see Files & Storage below).

Paths, permissions, and getting unstuck

Absolute paths start from the root, e.g. /data/ligand_libraries/set3. Relative paths start from where you are, e.g. ../results/run1. When in doubt, use pwd to check where "here" actually is.

Permissions: ls -l shows something like -rwxr-xr-x — read/write/execute for owner, group, and everyone else. You'll rarely need to change permissions, except making your own script runnable with chmod +x script.sh.

History: press ↑ to recall previous commands, type history to see a list, or press Ctrl+R to search your history interactively.

Getting help: man command opens the manual page; most commands also accept --help for a quick summary.

COMMON MISTAKES
  • rm -rf deletes permanently — no confirmation, no undo. Double-check your path before pressing Enter.
  • Wildcards are powerful and dangerous: rm * in the wrong directory deletes everything in it.
  • Linux is case-sensitive: Results/ and results/ are different folders.

Files & storage

Your laptop and Woody are two separate computers. Files don't move between them automatically — you have to transfer them deliberately, and you have to choose the right storage location once they're there.

LocationSizeWhat it's for
/home632 GB · personalYour scripts, environments, and small personal files. Your desk, not your warehouse.
/scratch3.7 TB · working spaceActive calculations, docking runs, temporary output. Not a permanent archive — clean up when a run is done.
/data73 TB · sharedLarge shared datasets: ligand libraries, reference structures, results worth keeping long-term.
CHEMISTRY NOTE
A single virtual screen against a library of tens of thousands of compounds can generate far more temporary output (poses, logs, intermediate files) than /home is built to hold. That's exactly why /scratch exists — and why the source ligand libraries themselves belong in /data, not copied into your home directory.

Moving files between your laptop and Woody

Use scp for individual files:

# Upload a file from your laptop to Woody
scp local_file.pdb username@woody:/home/username/project/

# Download a file from Woody to your laptop
scp username@woody:/scratch/username/results/output.csv .

For whole folders or large datasets, rsync is more robust — it can resume interrupted transfers and only copies what's changed:

rsync -avz local_folder/ username@woody:/data/username/project/
GOOD PRACTICE
  • Small scripts and environments → /home. Active runs → /scratch. Shared/large data → /data.
  • Never let /scratch hold the only copy of a result you care about — move anything worth keeping to /data or off the machine entirely.
  • Use rsync instead of repeated scp calls when moving large or growing folders.

Project organisation

A consistent folder layout means you — and whoever inherits your project — can understand it in five minutes rather than an afternoon.

project/
├── README.md          ← what this project is, and how to reproduce it
├── input/              ← starting structures, ligand lists
├── scripts/            ← your code
├── environments/       ← conda/venv definitions (see Software & Environments)
├── docking_runs/       ← raw run output (usually in /scratch)
├── results/            ← processed, kept output
└── analysis/           ← notebooks, figures, summaries

Your README.md doesn't need to be long. It should answer: what is this project, when did you start it, what environment does it need, and how would someone reproduce your last result?

GOOD PRACTICE
  • Use descriptive, underscore-separated names: 2026-07_kinase_screen, not test2.
  • Keep raw run output in /scratch, and copy only what you've verified matters into results/ in /data.
COMMON MISTAKES
Folders named final_v2_REAL_final, and one-off scripts nobody documented — including you, in three months.

Software & environments

Woody's system software is shared infrastructure. Isolating your own tools protects both your work and everyone else's.

DO NOT MODIFY SYSTEM PYTHON
Woody's system Python is version 3.6.8, and existing software (including cryo-related tools) depends on it exactly as it is. Never sudo pip install anything, and never install packages globally.

Use isolated environments instead

Conda or Mamba environments give you your own private, disposable Python setup per project — install whatever you need without touching the system, and without breaking anyone else's work. (A full walkthrough of installing and configuring scientific software — OpenEye, RDKit, and friends — is a good candidate for its own future chapter.)

Modules (Lmod)

Woody also has Lmod for a small number of shared libraries:

module avail        # list what's available
module load mpi/openmpi-x86_64
module list         # see what you currently have loaded

Currently available: mpi/openmpi-x86_64 and pmi/pmix-x86_64. Modules are a secondary tool here — your own conda/mamba environments will do most of the work.

COMMON MISTAKES
  • Global pip install outside of an environment.
  • Any use of sudo with pip or conda — you shouldn't need it, and if you think you do, ask first.

Looking for guides to specific installed tools (AlphaFold3, and more over time)? See the Software chapter.

Monitoring resources

With four GPUs and 64 threads shared across the group, checking what's free before you start is basic courtesy — and it saves you from launching a job into resources that are already spoken for.

CommandShows you
nvidia-smiGPU utilisation and memory usage, per card.
topLive CPU and memory usage by process. Press q to exit.
htopA friendlier version of top, if installed.
free -hTotal, used, and free RAM, in human-readable units.
df -hDisk space free on each mounted volume (/home, /scratch, /data).
du -sh folderTotal size of a specific folder — useful for finding what's eating space.
GOOD PRACTICE
Run nvidia-smi and free -h before launching anything large. If all four GPUs already show near-full memory, your job will either fail or slow everyone down — check first, or ask in the group chat.

Running long workflows

Woody currently has no job scheduler — no SLURM, no PBS, no automatic queue. That gives you flexibility, but also means nothing protects your job automatically, and nothing stops you from accidentally taking resources someone else needed. The practical consequence: if your SSH connection drops or you close your terminal, any job running in that session dies with it — unless you've protected it.

A typical docking/co-folding workflow

Protein → Preparation → Ligand library → Docking / Co-folding → Analysis → Experimental validation.

Keeping a job alive: tmux

HOW TO — run something long in tmux 
tmux new -s gpu2_screen_batch3     # start a named session
# ...run your job here...
# detach without stopping it: Ctrl+b, then d

tmux ls                            # list running sessions
tmux attach -t gpu2_screen_batch3  # reattach later, from anywhere

Your job keeps running after you detach — even after you close your laptop — because it belongs to the tmux session on Woody, not to your terminal connection.

screen works similarly and is a fine alternative if that's what you already know. For quick one-off jobs, nohup command & will also survive a disconnect, sending output to a file called nohup.out.

GOOD PRACTICE
  • Name your tmux sessions descriptively (tmux new -s kinase_dock_gpu1), not tmux new -s test.
  • With no scheduler enforcing fairness, a quick message to labmates about which GPU(s) you're using goes a long way.
